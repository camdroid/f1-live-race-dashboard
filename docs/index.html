F1 Race Tracker · Project documentation

How the pieces fit together

A set of live F1 dashboards built on FastF1 and Tom Shaw's Open Pit Wall (OPW). The heart is a bridge that connects to the official F1 SignalR timing feed, decodes the compressed telemetry channels, and re-broadcasts everything in OPW's WebSocket protocol on port 8765 — with record/replay so the whole stack runs offline between race weekends.

Companion doc: the Driver Tower design proposal covers the planned standings column for the track map.

Architecture

Three data sources, one shared display stack. Everything that speaks the OPW protocol goes through the bridge on port 8765; the terminal board talks to the F1 feed directly.

  • Green boxes — data sources. The live feed needs F1TV auth (via FastF1's internal get_auth_token); the historical API just needs network once, then it's cached.
  • Blue box — the bridge, the heart of the repo. Everything to its right works identically whether the bridge is live or replaying a recording.
  • Amber box — recordings, the offline test fixtures. Solid arrows carry live data; dashed arrows are alternative paths.

The bridge — live_opw_bridge.py

SignalR in, OPW WebSocket out. One process, three moving parts: a data source (live client or replay), a thread-safe LiveState, and a 10 Hz broadcast server.

LiveF1Client — the live source
Subscribes to 13 SignalR topics (timing, weather, race control, CarData.z, Position.z…). Compressed payloads are base64 + raw-deflate; _decode_compressed inflates them to JSON. Auth comes from fastf1.internals.f1auth.get_auth_token; --no-auth connects anyway with partial data.
LiveState — shared state + announcer
Per-driver telemetry, positions, stints, weather, session info — all behind one lock, snapshotted per broadcast tick. It also watches RaceControlMessages and TrackStatus and turns them into readable one-liners: 🚨 penalties, 💥 retirements, 🟨 safety car, 🟥 red flag.
OPWServer — the broadcaster
Serves ws://localhost:8765. Sends a welcome message on connect; clients reply with {"action": "subscribe", "channels": [...]}. Every 100 ms it snapshots state, builds one frame per channel, and sends each client only what it subscribed to.
ReplaySource — the offline source
Reads a recording and pushes each message through the same route_message path as live data, honouring original timing scaled by --speed, optionally with --loop. No auth, no network.

Broadcast channels

ChannelPayload
telemetry.drivers Array of per-driver frames: speed, rpm, gear, throttle, brake, DRS, tyre compound, and x/y/z position (metres). Also available per driver as telemetry.drivers.VER etc.
leaderboard Running order: position + driver code, sorted by TimingData.Position.
race_control The latest raw race-control message plus the full list of formatted announcements (the emoji-tagged penalty/incident lines).
telemetry.weather Track/air temperature, humidity, wind, and a DRY/WET rain state.
telemetry.lap Current lap number and elapsed stream seconds.

Telemetry decoding cheat-sheet

  • CarData channels — indices are strings: "0" rpm, "2" speed, "3" gear, "4" throttle, "5" brake (×100 to a percentage), "45" DRS. Constants live at the top of the file — reuse them.
  • Position scale — feed coordinates are 1/10 metre (POSITION_SCALE = 0.1). The bridge emits metres; FastF1 circuit geometry stays in 1/10 m, so the track map rescales when projecting.
  • Track status codes — 1 clear, 2 yellow, 4 safety car, 5 red flag, 6/7 VSC deployed/ending.
Design rule: one bad payload must never take down the feed. Every message goes through safe_route, which logs and skips malformed data. The real feed sends zeroed positions, partial payloads, and mid-session reconnects — treat all of it as normal.

Past-race animation — replay_past_race.py

Loads a completed session from the FastF1 API and steps the board lap by lap (1.5 s per lap, divided by --speed; --lap N jumps in). It reconstructs feed-shaped snapshots from the laps DataFrame — positions, lap/sector times with purple/green statuses, tyre stints, pit counts, and race-control flags. Gaps are approximated from best-lap deltas, which is fine for exercising the display but not real race gaps. Defaults to 2025 Monaco; needs network on first load, cached afterwards.

Track map — opw_track_map.py

A PySide6 window: live driver dots on the real circuit outline, with the race-control announcement feed underneath. It's an OPW client — feed it from the bridge (live or replay).

  • Circuit geometry comes from FastF1 telemetry of the fastest lap, loaded in a background thread. Since a live race isn't in the historical API yet, it falls back through candidates: requested session → same-year quali → last year's race → last year's quali → two years back. The layout is identical, so any hit works.
  • Positions → track dots — live x/y (metres) are projected onto the centreline by nearest point, giving a lap fraction the vendored _TrackMapWidget can draw. Circular ⇄ Real Track toggle; real view switches on automatically once geometry loads.
  • Zeroed-position guard — F1TV Access streams the position feed with all coordinates zeroed (GPS is gated to higher tiers). The map detects an all-zero frame and shows a status note instead of collapsing every dot onto the origin. Telemetry channels stay live regardless.
  • Reconnection — the WebSocket client retries with backoff (2 s → ×1.5 → max 15 s), so start order relative to the bridge doesn't matter.
  • Colours — currently a first-come-first-served palette copied from f1-race-replay. The Driver Tower proposal would replace this with real team colours.
  • Vendored widget — _TrackMapWidget is imported from the vendor/f1-race-replay submodule via sys.path. Don't edit the submodule; wrap or monkey-patch from this repo and log issues in vendor-issues.md.

Record & replay

The development loop for the whole stack: capture a live session once, then drive every dashboard from the file — no auth, no network, any speed.

# One line per feed message — relative seconds, topic, decoded payload:
{"rt": 0.0214, "topic": "TimingData", "data": {"Lines": {"1": {"Position": "3", …}}}}
{"rt": 0.1808, "topic": "CarData.z", "data": "…base64+deflate blob, kept compressed…"}

# Capture (start_live.sh does this automatically, timestamped):
.venv/bin/python live_opw_bridge.py --record recordings/session_$(date +%Y%m%d_%H%M%S).txt

# Replay through the identical live pipeline:
.venv/bin/python live_opw_bridge.py --replay recordings/session_20260726_080636.txt --speed 10 --loop
  • Same code path as live — replayed messages go through route_message exactly like the SignalR feed, so bugs reproduce faithfully. This is the intended way to verify changes (see AGENTS.md).
  • Recordings are fixtures — recordings/ is gitignored but holds real captured sessions, including the pathological data (zeroed positions, partial payloads) you want tests to cover. Snip representative lines into tests/fixtures/ rather than referencing full files.
  • Two formats exist — the bridge writes the JSONL above. pit_wall.py --record and the legacy live_timing.py write FastF1's str([topic, json, ts]) lines instead, which replay_session.py / fastf1.livetiming.LiveTimingData can load but the bridge's --replay explicitly rejects. Don't mix them.

Legacy one-shots

live_timing.py (raw FastF1 feed recorder) and replay_session.py (loads a recording or finished session and prints a fastest-laps summary) predate the bridge. They're kept as minimal FastF1 examples — reach for the bridge for anything real.

Launchers

Each script starts a broadcaster inside a named screen session, launches the telemetry trace and track map as background processes, then exec screen -r — it takes over the terminal. Run the Python entry points directly if you need your shell back.

ScriptScreenWhat it runs
start_live.sh [DRIVER] [ROUND] [YEAR] f1live Bridge in live mode, auto-recording to a timestamped file in recordings/. Refuses to start if port 8765 is taken — two bridges writing one recording corrupts it (lsof -iTCP:8765 -sTCP:LISTEN to check).
start_replay_live.sh FILE [DRIVER] [ROUND] [YEAR] [SPEED] f1replay Bridge in --replay --loop mode against a recording. The offline-development default. Same port guard.
start_replay.sh [DRIVER] [ROUND] [YEAR] opw OPW's own interactive broadcaster (python -m open_pit_wall) — navigate its menu, then play. Uses OPW's saved-data format, not this repo's recordings.

Defaults are VER Monaco 2026. Drivers are three-letter codes; rounds are FastF1 event names ("Monaco", "Canadian Grand Prix"). Detach with Ctrl-A D, reattach with screen -r f1live.

Docker

Headless variants of the same stack. docker compose up <service>; the FastF1 cache lives in the f1cache volume and ./recordings is bind-mounted.

ServicePortWhat it is
bridge8765 The live bridge, recording to recordings/live_session.txt. Point dashboards on the host at it.
pitwall— The terminal timing board, attached via docker attach / compose TTY.
replay— OPW's interactive replay broadcaster.
web-pitwall7681 The timing board in a browser via ttyd (xterm.js), writable.
web-replay7682 The OPW broadcaster TUI in a browser via ttyd.
trackmap— The Qt map via X11 forwarding — XQuartz + xhost +localhost on macOS, DISPLAY=$DISPLAY on Linux.
No auth on the web TUIs. ttyd serves ports 7681/7682 writable with no login and no TLS — they're meant to sit behind a reverse proxy (Caddy, nginx, Cloudflare Tunnel) that provides both. Don't expose them raw.

Working on the repo

The short version of AGENTS.md — the conventions that actually bite.

  • Setup — ./setup.sh once: inits the submodules, creates .venv, installs requirements.txt plus OPW as an editable install. Always use .venv/bin/python; there is no activation step, and the env/ directory is a stale second venv — ignore it.
  • Verify with a replay — after any change, run the bridge against the newest recording at --speed 10 and start the component you touched. That's the point of record/replay; don't wait for a live session.
  • Tests — there's no suite yet, but new work should add one: pytest under tests/. The testable seams are the pure layers — payload decoding, OPW frame building, and pit_wall.py's state/table builders — not the TUIs or Qt apps.
  • Vendor submodules are read-only — vendor/open-pit-wall and vendor/f1-race-replay track upstream. Wrap or monkey-patch from this repo's code, and log suspected upstream bugs in vendor-issues.md with a repro against a named recording.
  • Live-feed data is defensive territory — zeroed positions, partial payloads, reconnects. Handle missing data gracefully and surface a note in the UI rather than crashing.
  • Git — plain imperative one-line commit messages describing user-visible behaviour; work directly on main; never commit recordings/, caches, or venvs.
